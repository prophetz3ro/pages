Hello everyone!

In this write-up, I'll be solving the **Seized** challenge from CyberDefenders. This challenge focuses on **Linux memory forensics** and provides a good introduction to working with **Volatility 2**.

Before jumping into the investigation, it's worth discussing an important concept: **Volatility profiles**.

When analyzing a memory dump, Volatility does not automatically know how the operating system's kernel structures are organized in memory. To locate processes, network connections, loaded modules, and other artifacts, it needs information about the target kernel's internal data structures.

In Volatility 2, this information is stored in a **profile**. A profile contains metadata about the kernel, including structure definitions, field offsets, and symbol information. You can think of it as a blueprint that tells Volatility how to interpret raw memory.

On Windows, Volatility ships with many pre-built profiles because Windows kernels are relatively standardized. Linux is different. Distributions often use different kernel versions, custom patches, and configuration options, which can change the layout of kernel structures such as `task_struct`. As a result, a profile built for one Linux kernel may not work correctly with another.

For that reason, when performing Linux memory analysis with Volatility 2, we typically need to build a profile that matches the target system. This profile is generated from the kernel's debug information, which contains DWARF data describing structures, field offsets, and type definitions used by the kernel.

Volatility 3 takes a different approach and replaces profiles with **symbol tables**. Instead of relying on a pre-built profile, Volatility 3 consumes kernel debug information and converts it into JSON-based symbol files. The underlying data is largely the same—structure definitions, offsets, and symbols—but the framework handles it in a more flexible and maintainable way.

For this challenge, we'll be working with Volatility 2, so one of the first tasks will be identifying the kernel version and ensuring that the correct profile is available before starting the investigation.

# Question 2

**There is a command containing a strange message in the bash history. Will you be able to read it?**

Volatility provides the `linux_bash` plugin, which extracts the bash history directly from memory. Before running the plugin, we need to specify the correct Linux profile using the `--profile` argument.

The following command lists all available profiles:

```bash
python2 volatility/vol.py --info 
```

![Listing available profiles](/assets/images/posts/seized/profile_info.webp)

For this memory image, the correct profile is `LinuxCentos7_3_10_1062x64`.

Next, we can extract the bash history:

```bash
python2 volatility/vol.py -f temp_extract_dir/dump.mem \
    --profile=LinuxCentos7_3_10_1062x64 \
    linux_bash
```

While reviewing the output, I noticed a suspicious Base64-encoded string in one of the executed commands.

![Searching in bash history](/assets/images/posts/seized/linux_bash.webp)

To decode it, I simply copied the string and used the `base64` utility:

```bash
echo "c2hrQ1RGe2wzdHNfc3Q0cnRfdGgzXzFudjNzdF83NWNjNTU0NzZmM2RmZTE2MjlhYzYwfQo=" > base64_content
base64 -d base64_content
```

The decoded output reveals the hidden message.

# Question 7

**After changing the user password, we found that the attacker still has access. Can you find out how?**

I started by reviewing the process tree associated with the `ncat` bind shell to understand what programs the attacker executed.

```text
.ncat                2854
..bash               2876
...python            2886
....bash             2887
.....vim             3196
```

The `vim` process caught my attention, so I decided to inspect its memory. To determine the process memory layout, I used the `linux_proc_maps` plugin.

```bash
python2 volatility/vol.py \
    -f temp_extract_dir/dump.mem \
    --profile=LinuxCentos7_3_10_1062x64 \
    linux_proc_maps -p 3196
```

`linux_proc_maps` is the equivalent of viewing `/proc/<pid>/maps` on a live Linux system. It reconstructs every Virtual Memory Area (VMA) for the selected process from the memory image. A VMA represents a contiguous range of virtual memory that shares the same properties, including:

- Read, write and execute permissions
- Backing source (mapped file or anonymous memory)
- File offset (for file-backed mappings)

![Linux_proc_maps](/assets/images/posts/seized/proc_map.webp)

The mapping I was most interested in was the **heap**, since it stores dynamically allocated memory created by functions such as `malloc()` or C++ `new`.

To extract the heap contents, I used the `linux_dump_map` plugin.

```bash
python2 volatility/vol.py \
    -f temp_extract_dir/dump.mem \
    --profile=LinuxCentos7_3_10_1062x64 \
    linux_dump_map \
    -p 3196 \
    -s <heap_start_address> \
    -D <out_dir>
```

This plugin dumps the specified VMA to disk, allowing further offline analysis.

![Linux_proc_dump](/assets/images/posts/seized/proc_dump.webp)

After dumping the heap, I searched it with `strings` and found what appeared to be a Base64-encoded value.

![Base64 encoded flag](/assets/images/posts/seized/well_played.webp)

Decoding it revealed the flag:

```text
shkCTF{rc.l0c4l_1s_funny_be2472cfaeed467ec9cab5b5a38e5fa0}
```

```
c2hrQ1RGe3JjLmwwYzRsXzFzX2Z1bm55X2JlMjQ3MmNmYWVlZDQ2N2VjOWNhYjViNWEzOGU1ZmEwfQo=
```

Although this recovered the flag, it did **not** explain how the attacker was still able to access the system after the user's password had been changed.

I continued examining the extracted memory and eventually noticed the following command:

![Adding public key to authorized_keys](/assets/images/posts/seized/adding_key.webp)

The command appends an SSH public key to the user's `~/.ssh/authorized_keys` file and sets the correct permissions on that file.

```bash
echo "ssh-rsa AAAAB3..." >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

This is a classic persistence mechanism. By installing their public key into `authorized_keys`, the attacker can authenticate using the corresponding private key, bypassing password-based authentication entirely. As a result, changing the user's password does not revoke the attacker's access, since SSH public key authentication remains valid until the unauthorized key is removed.

# Question 8

**What is the name of the rootkit that the attacker used?**


## What is rootkit?

A **rootkit** is a collection of software or techniques designed to **hide the presence of malicious activity** on a compromised system while maintaining privileged access (typically root or administrator privileges).

The primary goal of a rootkit is **stealth**. Unlike malware whose purpose is to infect a system, a rootkit is usually installed **after** an attacker has already gained access. It allows the attacker to remain undetected while continuing to control the compromised machine.

Typical capabilities include:

- Hiding processes
- Hiding files and directories
- Hiding network connections
- Hiding kernel modules
- Hiding user accounts
- Intercepting system calls to manipulate program output
- Providing persistent privileged access

## Kernel-Mode Rootkits

A **kernel-mode rootkit** executes within the operating system kernel, giving it the same privilege level as the kernel itself.

Because almost every interaction between user-space applications and hardware passes through the kernel, a kernel rootkit can manipulate what applications see, making it significantly more powerful and difficult to detect than a user-mode rootkit.

## How they work

Kernel rootkits commonly modify or hook kernel functionality by:

- Hooking system calls
- Patching kernel functions
- Intercepting filesystem operations
- Intercepting network operations
- Hiding kernel modules
- Modifying kernel data structures

For example, when a user runs:

```bash
ps aux
```

the command eventually invokes kernel functions to enumerate processes.

A kernel rootkit can intercept those functions and remove selected processes from the returned list, making malicious processes invisible even though they continue to execute.

Similarly:

```bash
ls /tmp
```

may not display a malicious file because the rootkit filters it from the directory listing before the kernel returns the results.

## Why kernel rootkits are difficult to detect

Kernel rootkits operate with the highest privileges available on the system. They can alter the information returned to user-space tools, causing standard utilities such as:

- `ps`
- `ls`
- `netstat`
- `lsof`

to display false or incomplete information.

Since they manipulate the operating system itself, disk-based detection tools may also receive manipulated results.

## Memory Forensics

Kernel rootkits often cannot hide from **offline memory analysis**.

Frameworks such as **Volatility** analyze raw memory images and inspect kernel data structures directly instead of relying on potentially compromised operating system APIs.

For Linux, useful Volatility plugins include:

- `linux_check_modules` – compare loaded modules with kernel structures.
- `linux_check_syscall` – detect modified system call table entries.
- `linux_check_idt` – detect hooked interrupt descriptor tables.

By comparing multiple independent kernel structures, investigators can identify inconsistencies that indicate the presence of a kernel rootkit.

## Solution

As mentioned above we can use volatility plugins to detect rootkit. I used couple of them and finally I found something in linux_check_syscall.

![linux_check_syscall results](/assets/images/posts/seized/linux_syscall.webp)

`linux_check_syscall` detects hooked system calls by examining each entry in the kernel's `sys_call_table`. Every entry should normally point to a function within the Linux kernel itself (e.g., `sys_read`, `sys_open`). Volatility resolves the address stored in each syscall table entry and determines whether it falls within the kernel's code section or the code section of a loaded kernel module. If the address belongs to a module instead of the core kernel, the syscall is reported as **HOOKED**. For example, `HOOKED: sysemptyrect/syscall_callback` indicates that the syscall has been redirected to the `syscall_callback` function inside the `sysemptyrect` kernel module. Redirecting system calls in this way is a classic technique used by kernel-mode rootkits to intercept and manipulate kernel behavior.

## Summary

This lab focused on Linux memory forensics using Volatility to investigate a compromised system. During the analysis, I learned how to reconstruct process memory layouts with `linux_proc_maps`, dump specific VMAs using `linux_dump_map`, and recover useful artifacts such as encoded flags and attacker commands from process memory. The investigation also revealed a persistence mechanism where the attacker added an SSH public key to `~/.ssh/authorized_keys`, allowing continued access even after the user's password was changed. Finally, I explored kernel-mode rootkits by analyzing hooked system calls with `linux_check_syscall`, gaining an understanding of how Volatility detects syscall hooks by resolving function pointers to either the kernel or loaded kernel modules.
