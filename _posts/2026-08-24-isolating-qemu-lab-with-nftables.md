# Isolating My QEMU Lab with nftables

I use a Windows VM running under QEMU/KVM for CyberDefenders labs. The VM needs internet access, but it should not be able to reach devices on my home networks.

## Network layout

```text
VM network:        192.168.122.0/24
VM bridge:         virbr0
Host Wi-Fi:        wlo1
Local network:     192.168.50.0/24
Upstream network:  192.168.55.0/24
```

The VM uses libvirt NAT. NAT prevents other LAN devices from initiating connections to the VM, but it does not stop the VM from initiating connections to those devices. I therefore added explicit forwarding rules.

## VM isolation rules

I created `/etc/nftables.d/vm-guard.nft`:

```nft
table inet vm_guard {
    chain forward {
        type filter hook forward priority -10; policy accept;

        iifname "virbr0" oifname "wlo1" \
            ip saddr 192.168.122.0/24 \
            ip daddr { 192.168.50.0/24, 192.168.55.0/24 } \
            counter drop
    }
}
```

This blocks forwarded traffic from the VM network to both protected networks. Other forwarded traffic continues normally, so the VM retains internet access.

The chain uses priority `-10`, which runs before the ordinary priority `0` chain shared by Docker, libvirt and UFW. An earlier `drop` is final and cannot be overridden by a later `accept`.

## Host isolation rule

I also blocked the Ubuntu host from reaching the upstream network using `/etc/nftables.d/lab-guard.nft`:

```nft
table inet lab_guard {
    chain output {
        type filter hook output priority -10; policy accept;

        ip daddr 192.168.55.0/24 counter drop
    }
}
```

This rule uses the `output` hook because it applies to traffic generated by the host rather than forwarded VM traffic.

## Persistence

I load each table through a dedicated systemd oneshot service. For example, `/etc/systemd/system/vm-guard.service` contains:

```ini
[Unit]
Description=VM network isolation rules
After=ufw.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStartPre=-/usr/sbin/nft delete table inet vm_guard
ExecStart=/usr/sbin/nft -f /etc/nftables.d/vm-guard.nft
ExecReload=-/usr/sbin/nft delete table inet vm_guard
ExecReload=/usr/sbin/nft -f /etc/nftables.d/vm-guard.nft
ExecStop=-/usr/sbin/nft delete table inet vm_guard

[Install]
WantedBy=multi-user.target
```

`lab-guard.service` uses the same structure with `lab_guard` and `lab-guard.nft`.

I enabled both services:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now vm-guard.service
sudo systemctl enable --now lab-guard.service
```

I deliberately did not enable the standard `nftables.service` because the default `/etc/nftables.conf` contained `flush ruleset`, which could remove rules maintained by UFW, Docker and libvirt.

## Verification

I verified the active tables and counters:

```bash
sudo nft list table inet vm_guard
sudo nft list table inet lab_guard
```

From the VM, both protected networks were unreachable while internet access continued to work. After rebooting, both tables returned and their counters increased when blocked connections were attempted.

## Result and limitations

The setup provides persistent network isolation for my lab VM:

```text
VM -> 192.168.50.0/24  blocked
VM -> 192.168.55.0/24  blocked
VM -> Internet         allowed
```

This is one layer of protection rather than a complete malware sandbox. I also avoid shared folders, clipboard integration and unnecessary USB passthrough, use VM snapshots, and disconnect networking when a lab does not require it.
